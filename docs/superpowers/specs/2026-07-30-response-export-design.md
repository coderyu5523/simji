# 응답 데이터 추출 설계

**2026-07-30.** 검사 응답을 CSV 로 내보내는 기능. 용도가 다른 두 갈래로 나눈다.

## 배경

OY_MSI 는 **표준화 전 사전 검사**다. 데이터를 모아 나중에 규준표(T점수·백분위)를 만드는 것이
목적인데, **지금 응답을 꺼낼 방법이 전혀 없다.** 관리자 화면은 대시보드·회원·주문·검사 목록
넷뿐이고 응시 결과를 보는 화면 자체가 없다. 쌓이기만 하고 쓸 수가 없는 상태다.

기관 담당자 쪽도 명부를 화면으로만 볼 수 있어, 자체 정리·보고에 쓸 파일이 없다.

## 범위

**한다**

- 연구용 추출 (관리자) — 표준화 분석에 넘길 파일
- 기관용 추출 (담당자) — 자기 발급분 명부 파일
- `/admin/*` 인증 가드 — 지금 무인증이라 추출을 붙이면 그대로 공개된다
- 추출 감사 로그

**안 한다** (이번 범위 밖)

- 채점 엔진 일반화 — 두 번째 검사 사양이 나온 뒤에 한다
- 규준표 모델·소급 재채점 — 규준표가 생긴 뒤에 한다
- 관리자 화면에서 응시 결과 열람 UI — 추출만 먼저 한다

---

## 1. 연구용 추출 (관리자)

표준화 분석 도구(SPSS·R·파이썬)에 그대로 넣을 수 있는 형태. **1행 = 1응시.**

**범위**: 검사 1종을 골라 전체 기관·전체 응시. 제출 완료(`status='submitted'`)만.

**컬럼**

| 구분 | 컬럼 |
|---|---|
| 식별 | `attempt_id` (가명 ID — 이름·연락처 없음) |
| 검사 | `test_code`, `assessment_version`, `scoring_version` |
| 응시 | `submitted_at`, `age_at_test`, `gender`(`male`/`female`/`no_answer`) |
| 문항 | 문항별 원점수 — **`item_code` 를 컬럼명으로** (`DEP01`…`SAF06`). **SAF 포함** |
| 채점 | 영역별 원점수·등급(**SAF 영역 포함**), `overall_signal`, `safety_level`, `environment_level`, `general_case_code`, `final_case_code`, `score_status` |

**영역 점수는 `test_results.engine_result.factors` 에서 읽는다.** `test_results.area_scores` 컬럼은
SAF 영역이 의도적으로 빠져 있어(`OyMsiScoringEngine:84-88`) 연구용으로는 불완전하다.
`engine_result.factors` 가 SAF 를 포함한 내부 산출물이며 패리티 대상이다.

**이름을 넣지 않는다.** `test_attempts.nickname` 과 `vouchers.recipient_name` 둘 다 제외한다.
표준화 분석에 필요 없고, 있으면 유출 시 피해만 커진다.

**SAF 문항을 넣는다.** 안전 절단점을 산출하려면 자살·자해 문항 응답이 반드시 필요하다.
이 파일이 민감한 이유가 이것이므로, 아래 §3 의 가드와 §5 의 감사 로그가 전제다.

## 2. 기관용 추출 (담당자)

명부를 파일로 받는 용도. **1행 = 1응시.**

**범위**: **자기가 발급한 검사권의 응시분만.** 명부(`/my`)와 같은 인가 규칙을 쓴다
(`vouchers.user_id = auth()->id()`). 별도 권한 개념을 새로 만들지 않는다.

**컬럼**

| 구분 | 컬럼 |
|---|---|
| 식별 | 응시자 이름(`vouchers.recipient_name` → 없으면 `attempts.nickname`), 발급일, 제출일 |
| 응시 | 연령, 성별 |
| 문항 | 문항별 원점수 — **SAF 문항만 제외**, 나머지는 포함 |
| 채점 | 영역별 원점수·등급(**SAF 영역 제외**), `overall_signal`, `safety_level`(즉시/당일 표기), `environment_level` |

영역 점수는 `test_results.area_scores` 를 그대로 쓴다 — 이 컬럼은 이미 SAF 가 빠져 있어
기관용에 맞는다. 연구용과 읽는 곳이 다르다(§1 참조).

**이름을 넣는다.** 담당자가 이미 명부에서 보고 있는 값이고, 없으면 누구 것인지 몰라 쓸모가 없다.

**안전 문항(SAF) 원점수를 넣지 않는다.** 이 검사는 SAF 원점수를 **어떤 화면에도 노출하지 않는다**
— 엔진이 결과 컬럼에서 빼고(`OyMsiScoringEngine` §74-88), 보고서 조립에서 거르고, 데이터 단언으로
한 번 더 막는 3중 구조다. 엑셀만 예외를 두면 이 방어가 통째로 무의미해진다.
`SAF06 = 3`("최근 12개월 내 자살 시도 4회 이상")이 셀 한 칸에 찍혀 파일로 돌아다니게 된다.

대신 **안전등급은 넣는다.** 명부 배지로 이미 보이는 값이라 새로 새는 정보가 없다.
담당자는 "이 응시가 급하다"를 파일에서도 알 수 있고, 문항 단위는 결과 보고서에서 본다.

**제외 대상을 하드코딩하지 않는다.** 채점 룰에서 읽되, **두 조건의 합집합**으로 결정한다 —
① `safety_items` 키(`ScoringRuleSeeder` 의 `'safety_items' => ['SAF01'…'SAF06']`), **∪**
② `factors[area].included_in_overall === false` 인 요인에 속한 문항. 검사가 늘어도 이 코드는
안 고친다.

**두 조건 다 읽는 이유(fail-closed).** `safety_items` 하나만 봤을 때는, 개정판에서 SAF07 이
추가되거나 이 키가 통째로 빠지면 자해·자살 문항이 경고 없이 기관용 CSV 로 나갔다(2026-07-30
최종 리뷰 I-1). `included_in_overall` 은 같은 요인을 가리키는 별도 신호라, 한쪽이 낡거나
사라져도 다른 쪽이 계속 막는다. `safety_items` 가 없거나 `factors` 키 자체가 없는 검사(다른
채점 엔진)에서는 그 조건이 아무것도 제외하지 않는다 — 안전요인 개념이 없는 검사이기 때문이다.

## 3. 권한

### 3-1. 관리자 식별 — 신규

**지금 관리자를 식별할 방법이 없다.** `users.user_type` 은 `personal | institution` 둘뿐이다.

`users.is_admin` (boolean, default false) 을 추가한다. `user_type` 에 값을 하나 더 끼우지 않는
이유는, `user_type` 이 가입 유형(개인/기관)이라는 다른 축이고 화면 분기에 이미 쓰이고 있기 때문이다.
관리자는 그 축과 직교한다.

첫 관리자 지정은 SQL 또는 artisan 커맨드로 한다. 관리자 임명 UI 는 이번 범위 밖.

### 3-2. `/admin/*` 가드

`routes/web.php:114` 의 관리자 그룹 전체에 `auth` + 관리자 확인 미들웨어를 건다.
현재 주석("임시 — 인증 가드 없음, ⚠️ 실서비스 전 auth 미들웨어 필수")을 해소한다.

**이건 이번 작업의 전제다.** 가드 없이 추출을 붙이면 자살·자해 응답이 공개 URL 로 나간다.
프리뷰가 이미 인터넷에 떠 있으므로 실제 위험이다.

### 3-3. 기관용

새 권한 개념 없음. 명부와 같은 규칙(`vouchers.user_id = auth()->id()`)을 재사용한다.

## 4. CSV 형식

- **UTF-8 BOM** — 엑셀에서 한글이 깨지지 않고, 분석 도구도 그대로 읽는다
- **미응답은 빈칸.** `0` 으로 채우지 않는다. "답 안 함"과 "전혀 아니다(0점)"는 다른 값이고,
  섞이면 절단점 계산이 통째로 틀어진다. 엔진이 이미 미응답을 `null` 로 구분하고 있다(`OyMsiScoringEngine:32`)
- **역채점 전 원점수를 쓴다.** 분석은 원자료로 해야 한다. `FUT04~06` 등 긍정 문항이 역채점되므로
  채점용 값(`scored`)을 내보내면 원자료가 아니게 된다
- **스트리밍 응답**(`StreamedResponse`)으로 내보낸다. 응시가 쌓이면 메모리에 다 올릴 수 없다
- 파일명: `{test_code}_{용도}_{YYYYMMDD}.csv`

## 5. 감사 로그

민감 데이터 추출은 흔적을 남긴다. **누가·언제·어떤 검사·몇 건**을 로그로 기록한다.
별도 테이블을 만들지 않고 `Log::info` 로 남긴다 — 조회 UI 요구가 아직 없고, 있으면 그때 테이블로 옮긴다.

## 6. 구현 위치

| 대상 | 위치 |
|---|---|
| CSV 조립 | `app/Services/Export/ResponseExporter.php` (신규) — 두 갈래가 컬럼 구성만 다르므로 프로필로 분기 |
| 연구용 라우트 | `/admin/exports/{test}` (관리자 가드) |
| 기관용 라우트 | `/my/exports/{test}` (로그인 + 발급자 범위) |
| 진입점 | 연구용 = `admin/tests.blade.php` 검사 행에 버튼 / 기관용 = `my/index.blade.php` 명부 상단 |
| 관리자 가드 | `app/Http/Middleware/EnsureAdmin.php` (신규) |

`ResponseExporter` 는 검사 종류를 모른다. 문항 목록은 `test->items`, 제외 대상은 룰의
`safety_items`, 결과는 `test_results`(기관용) 또는 `test_results.engine_result.factors`(연구용)
에서 읽는다. OY_MSI 분기를 두지 않는다.

## 7. 테스트

- 연구용에 SAF 문항이 **있다**
- 기관용에 SAF 문항이 **없다** — 부재 단언은 SAF 응답이 실제로 존재하는 응시로 검증한다
  (빈 데이터로 통과하는 공허한 단언 금지)
- 기관용이 **남의 발급분을 포함하지 않는다** — 다른 사용자 발급 응시를 넣고 확인
- 미응답이 빈칸으로 나온다 (`0` 아님)
- 역채점 문항이 역채점 **전** 값으로 나온다
- 비로그인·비관리자가 `/admin/exports/*` 에 접근하면 차단된다
- `safety_items` 키가 없어도 `included_in_overall=false` 요인의 문항은 계속 제외된다,
  거꾸로 그 요인 정의가 없어도 `safety_items` 목록이 있으면 계속 제외된다(두 조건의 독립성)
- 이름이 연구용에 **없다**
- 연구용에 SAF **영역 점수**가 있고, 기관용에는 없다 (읽는 소스가 다른 것이 실제로 작동하는지)

가드 회귀 확인: 새 가드를 기존 검사 앞에 세우면 기존 테스트가 통과한 채 무력해질 수 있다.
가드를 일시 제거해 실제로 깨지는지(뮤테이션) 확인한다.

## 8. 미결

- **연구용에 기관 정보를 넣을지** — 표본 특성 분석에는 유용하나 재식별 위험이 있다.
  이번엔 넣지 않는다. 표준화 분석 담당자가 요구하면 그때 다시 본다.
- **동의 범위** — `consent_records` 에 민감정보 동의가 남지만, 그 동의가 "표준화 연구 활용"까지
  포함하는지는 문안 확인이 필요하다. 운영 판단 사항으로 넘긴다.
- 관리자 임명 UI — 이번 범위 밖. SQL/커맨드로 지정.
