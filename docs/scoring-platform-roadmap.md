# 채점 플랫폼 일반화 로드맵

**작성 2026-07-30.** 심지 채점 엔진을 "OY_MSI 전용"에서 "검사를 붙여 쓰는 플랫폼"으로 바꾸는 순서.
5단계를 **순차적으로** 진행한다. 각 단계는 별도 설계 문서를 가진다.

---

## 왜 하는가

OY_MSI 는 **표준화 전 사전 검사**다. 데이터를 모아 나중에 단디 검사 형태의 T점수·백분위를
만드는 것이 목적이므로, **지금의 채점 형태를 플랫폼 표준으로 굳히면 안 된다.**

검사 문서 자신이 그렇게 말한다 (003 Ⅳ-2):

> 이 기준은 단디 플랫폼의 신호등 체계를 적용한 **연구용 임시 기준**이다. 검사도구의 최종
> 절단점은 표준화 표본을 대상으로 민감도, 특이도, ROC 분석, 상담자 판단 및 외부 준거검사와의
> 관계를 검토한 후 확정해야 한다.

지금 엔진은 OY_MSI 의 생김새(영역당 6문항 · 0~3점 4점척도 · 신호등 3단계)를 코드 상수로
박아 두었다. 검사가 하나뿐인 지금이 갈아엎기 가장 싼 시점이다.

## 목표 구조 — 단디 모델

단디(`C:\work\단디`)에 이미 있다. **제네릭 엔진 + 검사별 레시피.**

- `score/score_lib.php` — 146줄 범용 엔진
- `score/def_{CODE}.php` — 검사별 레시피 11종 (KMSIA, KDII2, KEBIIP, KPAS, ADHDSIP, …)
- `sql/ts_schema.sql` — 같은 모델을 DB 테이블로 정규화한 스키마 (`ts_test`/`ts_scale`/`ts_question`/`ts_scale_pair`)

레시피가 표현하는 것:

| 개념 | 내용 |
|---|---|
| 영역 `scale` | `items`(문항 번호 목록, **개수 자유**) / `pairs`(비일관성) / `composite`(자식 합산) |
| 종합 `composite` | `sum_children`(원점수 합) / `sum_tscores`(표준점수 합) / `avg_children`(평균) / `conditional`(필드값 분기) |
| 규준표 `norm` | 원점수 → 환산표 룩업(T점수·척도점수·등가연령). `table_age` 로 월령 밴드별 표 분기. **`null` 이면 원점수만** |
| 등급 `grades` | 점수 범위 → 라벨. 검사마다 단계 수가 다름 (KMSIA 5단계 / KDII2 7단계) |
| 방향 `direction` | `pos`/`neg`/`info`. 긍정척도는 높을수록 우수, 부정척도는 높을수록 위험 |
| 명부 `report` | 영역별 표시 칸(원점수/T점수/판정/등가연령) 레이아웃 |

실제 다양성 (이 폭을 감당해야 한다):

- **KMSIA** — 영역별 문항 수 제각각(우울 9 / 공포 6 / 강박성향 4), 5단계 등급, pos·neg 등급표 반전
- **KDII2** — 210문항, 영역당 35문항, 결과가 **척도점수(1~19) + 등가연령(개월) + 발달지수(DQ)** 3종, 7단계 등급, 규준표가 **8개 월령 밴드**로 분기

## 유리한 조건

- **원자료가 이미 재채점 가능한 형태로 쌓인다.** 문항별 응답이 `attempt_answers` 에 원점수로
  저장되고, 응시마다 `assessment_version`·`scoring_version` 이 찍힌다. 표준화 후 소급 재채점 가능.
- **패리티 안전망이 있다.** `tests/Feature/OyMsi/ReferenceParityTest.php` — 엔진을 갈아엎어도
  같은 답을 내는지 검증할 수 있다.
- **엔진 교체 지점이 이미 있다.** `tests.scoring_engine` → `ScoringService::ENGINES` 매핑.
- **규준표가 아직 없는 검사를 모델이 이미 지원한다.** 단디도 `norm=null` 영역이 있다.
  OY_MSI 는 그대로 `norm=null` + 임시 등급표로 표현되고, 규준표가 생기면 `norm` 만 채우면 된다.

## 순서 (순차 진행)

### 1. 문안 테이블 검사별 분리

`interpretation_templates` 에 `test_id` 가 없다
(`2026_07_28_000002_create_oy_msi_support_tables.php:9-18`). 키가 `result.YOUTH.DEP.GREEN.meaning`
같은 **전역 키**라, 다른 검사에 DEP(우울) 영역이 있으면 문안이 충돌한다. **검사 두 개째부터 터진다.**

다른 단계와 무관하게 선행. 규모가 작아 2번 안에 같이 처리 가능.

**완료 조건**: 같은 template_key 를 쓰는 검사 2개가 서로 다른 문안을 갖는 테스트가 통과한다.

### 2. 채점 엔진을 레시피 모델로 재작성 ← **지금 여기**

6·18·3단계 상수를 걷어내고 영역·척도·규준표·등급·방향을 전부 레시피에서 읽게 한다.
나머지 단계가 전부 여기에 달려 있다.

**완료 조건**: `ReferenceParityTest` 가 새 엔진에서 0-diff 로 통과한다.

### 3. 규준표 데이터 모델 이식

단디 `ts_*` 스키마를 심지로. 지금은 비어 있어도 자리를 만들어 둔다.
`norm_type` 은 `table`(환산표)과 `formula`(평균·SD) 둘 다 지원해야 한다.

**완료 조건**: 규준표를 가진 가상 검사 1종이 T점수를 산출한다.

### 4. OY_MSI 를 새 모델로 이전

레시피화. 패리티 테스트로 0-diff 확인하며 진행.

**완료 조건**: 라이브 OY_MSI 가 새 엔진으로 돌고 기존 응시 결과가 재채점 시 동일하다.

### 5. 명부·결과 화면 일반화

검사별 `report` 레이아웃을 레시피에서 읽는다. 검사마다 표시 칸이 다르다(원점수/T점수/판정/등가연령).

이 단계에 **명부 필터**가 딸려 온다 — 원래 출발점이었던 "급한 응시만 걸러 보기".
필터 축은 검사별 이름(OY_MSI 의 `안정·예방군` 등)이 아니라 **검사 공통 축**이어야 한다.
검사가 늘 때마다 칩 종류가 늘면 명부가 못 버틴다.

**완료 조건**: 서로 다른 모양의 검사 2종이 한 명부에 섞여도 표시와 필터가 성립한다.
